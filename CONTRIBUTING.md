# Разработка

Стек: Rust, Tauri 2, Svelte 5, TypeScript, Vite. Фронтенд — `frontend/`,
конфигурация Tauri — `tauri.conf.json`. В проекте используются окончания строк LF.

Для Windows нужны Node.js 24, Rust MSVC, Visual Studio Build Tools с C++ и WebView2.

## Локальный запуск

Из корня репозитория:

```bash
cd frontend
npm ci
npm run tauri dev
```

Закрытие окна сворачивает приложение в трей. Завершение — пункт «Выход» в меню трея.

## Проверки

```bash
cd frontend
npm ci
npm run check
npm run build
cd ..
cargo test --locked
```

Фронтенд необходимо собрать перед Rust-тестами: Tauri встраивает его ресурсы.

## Windows-установщик

Собирать в Windows PowerShell/CMD с Windows-версиями Node.js и Rust:

```powershell
cd frontend
npm ci
npm run tauri -- build --bundles nsis -- --locked
```

Результат: `target/release/bundle/nsis/*-setup.exe`. При явном `--target`
в путь добавляется целевая платформа. Обычная сборка в WSL не создаёт Windows-установщик.

NSIS устанавливает приложение для текущего пользователя и при необходимости
скачивает WebView2. Windows Authenticode пока не используется.

## CI и релизы

Workflow `.github/workflows/windows.yml` собирает Windows x64:

- PR и push в `main`: проверка типов, сборка фронтенда, Rust-тесты и сборка
  приложения без установщика.
- **Actions → Windows CI and release → Run workflow**: сборка установщика
  и публикация релиза. Ветка `main` — стабильный релиз, остальные — prerelease.
- Комментарий `/prerelease` в открытом PR: выпуск пререлиза с текущего SHA ветки.
  Нужен write-доступ; PR из форков не поддерживаются.

Ссылка на релиз находится в Summary job публикации. Название — `SaveHub <версия>`,
например `SaveHub 0.2.2`.

### Версия приложения

Перед стабильным релизом повысьте версию: PATCH для исправлений, MINOR для новых функций.

1. Обновите `Cargo.toml` (`[package].version`) и `tauri.conf.json` (`version`).
2. Выполните `cargo check`, чтобы обновить запись `savehub` в `Cargo.lock`.
3. Включите все три файла в коммит.

Версия должна быть выше предыдущего стабильного релиза. CI проверяет версии,
но не повышает их автоматически.

### Подпись обновлений

Для стабильного выпуска в GitHub Actions должны быть настроены:

| Тип | Имя | Значение |
| --- | --- | --- |
| Variable | `SAVEHUB_UPDATER_PUBLIC_KEY` | Публичный ключ Tauri |
| Secret | `TAURI_SIGNING_PRIVATE_KEY` | Приватный ключ Tauri |
| Secret | `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | Пароль ключа |

Создание ключей описано в [документации Tauri Updater](https://v2.tauri.app/plugin/updater/).
Ключи создаются один раз для проекта; приватный ключ и пароль не хранятся в Git.
Обычная разработка и пререлизы не требуют приватного ключа.

Стабильный релиз содержит установщик, `.sig` и `latest.json` и назначается Latest
после загрузки всех файлов. Пререлизы в канал автообновлений не входят.

Для локальной сборки с подписью задайте те же переменные окружения и из `frontend/` выполните:

```powershell
node ../.github/scripts/prepare-updater.mjs
npm run tauri -- build --bundles nsis --config target/updater/tauri.updater.conf.json -- --locked
```

## Работа с кодом

### Контракт фронт ↔ бэк

Команды находятся в `src/api/`, вызовы фронтенда — в `frontend/src/lib/api.ts`.
Команды вызывают сервисы и сценарии; ошибки переводятся в `ApiError`.

Правила:

- ручка — `#[tauri::command]` в `src/api/<экран>.rs`, регистрируется в `app::start` (`generate_handler!`);
- ручка тонкая: вызывает сервис или сценарий, переводит доменные структуры в DTO;
- DTO — структуры с `#[serde(rename_all = "camelCase")]` рядом с ручкой; их TS-двойники — во `frontend/src/lib/types.ts`, менять вместе;
- ошибки — `ApiError`: `NotImplemented`, `Rejected` (текст покажется пользователю как есть, например «Идёт игра, переключение недоступно»), `Internal`;
- долгие ручки (git, копирование сохранений) — `async fn`: синхронные ручки Tauri выполняет в главном потоке, окно зависнет;
- когда данные меняются не по запросу фронта (RepoWorker, запуск игры, трей) — шлем событие из `src/api/events.rs` (`app_handle.emit(...)`), фронт перезапросит данные.

| Экран | Ручки | Что подключить |
| --- | --- | --- |
| Игры | `list_games`, `add_game`, `set_game_save_path` | GameService, RuntimeState (запущенные игры) |
| Профили | `list_profiles`, `switch_profile`, `create_profile`, `delete_profile` | ProfileService, workflows::SwitchProfile |
| Сохранения | `list_save_history`, `restore_save` | SaveService / сохранения, сценарий отката |
| Настройки | `get_settings`, `update_settings`, `set_github_token` | хранилище Settings, системное хранилище токена |
| Запуск и обновления | `get_app_preferences`, `save_app_preferences`, `get_update_status`, `check_for_updates`, `install_update` | реализованы; настройки в `updates.json` |
| Шапка, трей | `get_sync_status`, `sync_now` | RepoWorker |
| Конфликты | `list_conflicts`, `resolve_conflict` | RepoWorker, сценарий разрешения конфликта |

Меню трея (`src/app/tray.rs`) читает профили и состояние процессов из доменных хранилищ; переключение использует тот же workflow, что и API.

## Архитектура, дизайн

Структура проекта

- `frontend/`: статика фронтенда
- `src/`:
  - `adapters/`: низкоуровневые адаптеры для взаимодействия с FS, git, процессами
  - `api/`: tauri-хэндлеры ("бэкенд"). Специальные функции, которые вызываются из tauri. Должны вызывать сервис или workflow в зависимости от сложности логики. Сами по себе - легковесные.
  - `app/`: корень и входная точка приложения. Читает и проверяет файл(ы), инициализирует структуры, сервисы, поднимает `tauri` и фоновый воркер.
  - `background/`: фоновый(-е) процесс(ы). В базовом виде - "следилка" за файлами. Реагирует на изменения, вызывает нужные сценарии (workflow) или сервисы.
  - `domain/`: доменные структуры (игры, профили)
  - `services/`: основная логика. GameService, ProfileService, SaveService, .... Каждый метод делает простое, гранулярное действие: "добавить новый профиль", "получить список всех игр".
  - `workflows/`: сценарии. Для сложных действий, по типу переключения профиля, требуется задействовать несколько сервисов - для того, чтобы не сорить ответственностью, такие сложные сценарии выносятся сюда.

`services/` и `domain/` не должны зависеть от Tauri или контрактов фронтенда.

### Взаимодействие

```text
Интерфейс ----> API ---+
                       |
                       +--> сервисы -> адаптеры
                       |
                       +--> сценарии -> сервисы -> адаптеры
                       |
Repo Worker -----------+
```

### Хранение данных внутри приложения

Чтобы не превращать хранение в кашу, предлагается организовать хранение данных следующим образом:

Хранилище есть структура, содержащая _внутри себя_ `RWMutex`.

Должны быть:
- Catalog (игры, профили, пути, настройки)
- RuntimeState (запущенные игры, подобные состояния "сейчас")
- Settings (базовые настройки: путь до репозитория, ссылка на удаленный репозиторий, локальные пользовательские данные)

Хранилища должны **создаваться** и **заполняться** в `app::start`, оборачиваться в `Arc` ([документация](https://doc.rust-lang.org/std/sync/struct.Arc.html)) и **передаваться** в конструкторы сервисов, где они нужны.

Хранилища должны **обновляться** по мере работы приложения: при разных пользовательских сценариях, рано или поздно вызывается какой-то сервис, этот сервис в свою очередь обращается к хранилищу и обновляет данные.

## Форма настройки игр

`GamesScreen` / `GameForm` используют команды из `api.ts`. Контракт добавления и
изменения: `name`, `exePath`, `savePath`. `update_game` заменяет прежнюю заглушку
`set_game_save_path`; `get_game_status` принимает `gameId`, как в PR #16.
При интеграции #16 сохранить отдельный `exePath` вместо подстановки `savePath`.

`list_games` дополнительно возвращает `exePath`, `exeMissing`, `savePathMissing`,
`pathScope` (`shared/local/ignored`) и `processStateKnown`. `found` означает только
наличие путей, не остановленную игру. `resolve_game_paths` принимает `gameId`,
`action` (`useLocal/updateRepository/ignore`), `exePath`, `savePath`.
`validate_game_paths` возвращает ошибки полей, `suggest_save_dirs` — название и
существующие папки или `null`. Проверки путей и поиск выполняются вне UI-потока.

Список игр хранится в отдельном репозитории `<app_data_dir>/catalog/`: ветка
`main`, единственный отслеживаемый файл `games.json` (массив объектов `Game`,
отсортированный по UUID). Служебная ветка и worktree не используются.
Профили и сохранения не входят в этот конфиг. `local_config.json` хранится
рядом, вне Git; локальные пути и игнорирование сохраняются между запусками.

Для подключения создайте **отдельный пустой репозиторий** GitHub без README
и задайте его HTTPS-адрес в настройках «Список игр». `catalogRepoUrl` независим
от `repoUrl` сохранений. Используется сохранённый токен GitHub (системное
хранилище реализовано для Windows). На других ОС доступ без токена возможен
для чтения публичного репозитория; отправка в GitHub требует авторизации.
К уже существующему каталогу подключайтесь до добавления игр на новом ПК.
Адрес проверенного `origin` автоматически не заменяется. Если первое получение
или проверка конфига не удались, первоначальная привязка откатывается: ошибочный
адрес можно исправить в настройках.

При добавлении, изменении, удалении игры или выборе `updateRepository`
приложение атомарно записывает конфиг и создаёт коммит. Без сети данные остаются
на ПК. Неудачный commit/push виден в статусе каталога; повторы идут через 1, 2, 4, 8,
15 минут, затем раз в 15 минут. Повтор push не создаёт новый коммит. Каталог
обновляется при запуске, перед изменением и после него, при смене адреса или
токена, кнопкой «Синхронизировать список» и планово раз в 15 минут.
Без адреса репозитория воркер ждёт сигнала. Ошибка прямой синхронизации также
перепланирует повтор; смена настроек будит воркер немедленно. Git-операции
выполняются на рабочем потоке под общей для этого каталога блокировкой.
Каталог данных также защищён межпроцессной файловой блокировкой на всё время
работы приложения: вторая копия не может открыть его для записи.

Общие и локальные изменения сохраняются под одной блокировкой до commit/push.
При ошибке записи общего конфига прежний локальный конфиг восстанавливается;
если восстановление также не удалось, UI явно сообщает о частичном сохранении.
Это обработка ошибок записи, а не атомарная транзакция двух файлов при аварийном
завершении процесса между заменами. Настройки приложения проверяются и
записываются одним снимком до обновления состояния в памяти.

Удалённый JSON проверяется до fast-forward: пустые обязательные поля,
повтор UUID, посторонние файлы и symlink вместо конфига отклоняются.
Расхождение историй останавливает синхронизацию без reset/force-push и потери
локальной версии. Пока требуется вручную объединить `games.json` в ветке
`main` локального каталога, закоммитить и повторить синхронизацию. Автоматического
разрешения конфликтов нет. Не удаляйте локальный клон с неотправленными коммитами.

`GameService` сохраняет каталог и локальные решения. `catalog_git` отвечает
за отдельный Git-репозиторий; `background/catalog` — за периодическое обновление.
`get_catalog_status` и `sync_catalog` независимы от будущей синхронизации сейвов.
`games-changed` испускается только при фактическом изменении каталога или
локальных решений. Это возможно и при частичной ошибке — например, новый
каталог получен, но push не удался. `catalog-status-changed` обновляет только
статус; ошибка без изменения данных не перезагружает список. Перенос сейвов
и junction этим экраном не выполняются.

Изменение существующей игры, путей и игнорирования требует известного
состояния процессов; при неизвестном возвращается `ProcessesUnknown`.
Первичная регистрация игры остаётся доступной. `background/processes` опрашивает
ОС каждые 2 секунды. До успешного опроса и при его ошибке кнопки редактирования
заблокированы с пояснением. Адаптер перечисления процессов поддерживает Windows
и Linux; на macOS состояние остаётся неизвестным.

Экран запускается вместе с приложением через `npm run tauri dev` из `frontend/`.
Все вызовы идут через единый `api.ts` в Tauri-команды; отдельного режима тестовых игр нет.

База подсказок и инструмент обновления: `tools/save-manifest/README.md`.

## Первый запуск и доступность функций

`get_app_features` (`src/api/features.rs`) сообщает, какие пользовательские сценарии
подключены в этой сборке. Это не статус подключения к GitHub. Включайте соответствующее
поле только вместе с рабочими командами и хранилищами: `sync`, `profileSwitch`,
`saveHistory`, `conflicts`, `persistentGames`, `persistentProfiles`. Обновляйте Rust и TS контракт вместе.
При подключении RepoWorker также замените временно отключённые действия трея реальными.

Первый запуск на экране игр проверяет сохранённые настройки и текущий список игр.
Сохранённый токен и заполненный URL не считаются успешной авторизацией или синхронизацией.
Статус, история и конфликты читаются из сервисов; демонстрационные данные
в рабочие ручки не добавляются. При ошибке чтения доступности
функций интерфейс предлагает повторить запрос, не предполагая успешное подключение.

При интеграции ветки каталога обновите временные сообщения о регистрации игр и профилей
вместе с фактическим хранением. `persistentGames` и `persistentProfiles` включаются независимо после подключения
постоянного хранения игр и профилей соответственно.
## Ярлыки и запуск игр

На экране «Игры» доступны «Запустить» и «Ярлык на рабочий стол» (Windows).
Ярлык называется `<Название игры> — SaveHub.lnk`, без UUID в видимом имени.
При совпадении имени существующий файл не заменяется. Иконка берётся из exe игры.
Ярлык `.lnk` указывает на установленный `savehub.exe --launch-game <UUID>` с иконкой
игры. SaveHub сначала выполняет подготовку, затем запускает exe без командной
оболочки, с рабочей папкой рядом с exe. Уже работающий экземпляр принимает запрос
через [Single Instance](https://v2.tauri.app/plugin/single-instance/).
При вызове ярлыка главное окно не открывается и не разворачивается. Подготовка
и успешный запуск проходят без окон; компактный диалог появляется только при выборе
профиля или ошибке запуска. После успешного запуска диалог скрывается, SaveHub
продолжает слежение в трее. Закрытие главного окна или диалога во время
подготовки отменяет запуск, в том числе при незавершённой сетевой проверке.
Для постоянных ярлыков используйте установленную сборку: перемещение/удаление
исполняемого файла SaveHub делает прежний ярлык недействительным.

Локальная регистрация ярлыка сохраняется в `app_data_dir/launchers/<UUID>.json`:
название, ID и эффективные пути на этом ПК. При запуске старого ярлыка отсутствующая
игра импортируется через `GameService` в постоянный каталог с прежним UUID,
поэтому обновление каталога и перезапуск её не удаляют. Существующая запись
каталога имеет приоритет над сохранённой копией ярлыка. Это
локальная копия на момент создания, не синхронизация каталога; после смены путей
удалите старый ярлык и создайте новый. Чужие файлы рабочего стола не заменяются.
Каталог профилей сохраняется локально в `profiles.json`, активный UUID — в `active-profile.json`.

Настройка `askProfileBeforeLaunch` включена по умолчанию, в том числе при чтении
старого `settings.json`. При наличии нескольких профилей открывается выбор и
доступна отмена. Выбор другого профиля вызывает `SwitchProfile` до запуска игры.

Распределение ответственности:

- `api/launch.rs`: команды и DTO, `app/launch.rs`: CLI, состояние запроса, обновления
  SaveHub и выбор профиля. Проверка обновлений перед игрой включается отдельно через
  `checkBeforeGameLaunch` в настройках обновлений; по умолчанию выключена, в том числе
  для старого updates.json. Требуется настроенный ключ подписи. Результат/ошибки
  доступны в настройках обновлений, проверка не блокирует запуск игры при ошибке.
  Установка обновления по-прежнему требует отдельного действия в настройках.
- `workflows/launch_game.rs`: выбор профиля, переключение и привязка сохранений
  перед запуском. Запуск и файловые операции используют общий mutex. Полный
  сетевой сценарий с lease и проверкой актуальности перед каждым запуском пока
  не подключён; запуск текущего профиля использует локальные файлы.
- `services/process.rs`: сериализация опроса/запуска, защита от повторного старта,
  дочерние процессы и восстановление локальной регистрации. `adapters/process.rs`:
  перечисление процессов ОС, запуск, создание Windows Shell Link.
- `background/processes.rs`: опрос каждые 2 секунды, обновление `RuntimeState` и события
  `games-changed`/`game-process-changed` (`gameId`, `state`, `pid`, `error`).
  Ошибка опроса сбрасывает состояние в неизвестное. Слежение продолжает работать в трее.

Сопоставляется полный путь exe; для недоступного ОС пути применяется консервативное
сравнение имени процесса. Отслеживается также удерживаемый дочерний процесс. Лаунчеры,
которые завершаются и передают игру другому exe, требуют отдельной настройки/интеграции;
завершение лаунчера само по себе не доказывает окончание игровой сессии.
Распределённая блокировка хранилища пока не подключена к запуску. При настроенном локальном репозитории запуск привязывает папку сохранений к текущему профилю.

Проверка на Windows: создать ярлык для exe с пробелами/кириллицей, закрыть SaveHub,
запустить ярлык, повторить при уже открытом SaveHub, проверить смену статуса после
завершения процесса. С двумя профилями проверить выбор/отмену, отказ смены профиля и
выключение выбора в настройках. В Rust-тестах Windows проверяется создание `.lnk`
и отказ перезаписи существующего файла.

SaveHub задаёт явный Windows AppUserModelID `io.github.savehub` до создания окон:
игровой ярлык с иконкой exe не должен определять иконку/группу самого SaveHub на панели
задач. Консоль отключена у dev- и release-сборок SaveHub; дочерние exe создаются с
`CREATE_NO_WINDOW`. GUI-окно самой игры этот флаг не скрывает.
Технические сведения о PID, недоступных снапшотах/блокировке и ключе обновлений
перенесены в DevNote (только dev). Настройки отправки сохранений и автоматической
смены профиля отмечены недоступными до реализации соответствующих сценариев.

Регистрация ярлыка сначала записывается во временный файл и публикуется по UUID
только после успешного создания .lnk. Ошибка создания не меняет старую регистрацию;
если публикация регистрации не удалась, созданный ярлык удаляется. Ошибки отката
возвращаются вызывающему коду, временные записи не используются для запуска.

## Репозитории профилей

`RepoService` реализует независимые ветки и worktree профилей, контрольные точки,
архивирование при удалении, разрешение конфликтов и lease. `RepoOperations`
подключает эти операции к фоновому воркеру; проверка неотправленных коммитов
сравнивает локальную ветку с `origin/<branch>` без сети и checkout.
Операции `ProfileService`, смена настроек и воркер используют общий mutex;
внутренняя блокировка RepoService отдельно сериализует его Git-операции.

Метаданные профилей в `savehub/catalog` не читают и не заменяют список игр:
его хранением и отдельным репозиторием по-прежнему управляет `GameService`.
Создание и удаление профилей работают через RepoService. Метаданные и активный
профиль сохраняются локально; их обмен между ПК через `savehub/catalog` пока
не подключён к UI. `persistentProfiles`, `profileSwitch`, `saveHistory` и
`conflicts` включены; полный сетевой сценарий `sync` остаётся выключен.


## Сохранения и переключение профилей (0.7.0)

`SaveService` использует `games/<GameId>` в существующем worktree профиля.
В настройках нужен абсолютный путь к уже созданному локальному Git-репозиторию
сохранений. Автоматическое первоначальное клонирование из экрана настроек пока
не подключено. Без URL удалённого репозитория переключение работает локально;
при заданном URL оно получает и применяет обновления целевого профиля, а ошибки
сети или конфликты останавливают переключение.

Первый импорт копирует файлы в хранилище активного профиля. Новый профиль
получает пустую папку. При привязке исходный обычный каталог переименовывается
в соседний `.savehub-original-<UUID>` и сохраняется; вместо него создаётся junction
на Windows или symlink на Unix. Если обычная папка и уже существующие данные
профиля различаются, операция отказывается выбирать победителя: нужно сохранить
обе папки и вручную согласовать содержимое. Посторонние и вложенные ссылки
отклоняются. `unbind` возвращает обычную копию, сохраняя управляемый каталог.

Локальные снимки — `<git metadata>/savehub/snapshots/<SaveId>`, индекс —
`index.json`. UUID проверяются до построения путей; индекс публикуется после
полного копирования. Снимки не входят в Git-историю и не синхронизируются.
Их причины: `BeforeSwitch`, `AfterSession`, `BeforeRestore`, `Conflict`,
`FileChanged`. Автоматическое создание `AfterSession` подключено к завершению
отслеживаемой игры, только для уже привязанных сохранений. Отдельный watcher
реализован как polling-адаптер; RepoWorker сохраняет собственное периодическое
сканирование и не зависит от этого адаптера.

История и восстановление подключены к обоим вариантам API (`list_saves` /
`choose_save` и `list_save_history` / `restore_save`). Перед восстановлением
всегда создаётся `BeforeRestore`, даже если старый клиент передал
`createSave=false`. Восстанавливать можно только в активный профиль снимка.
Замена идёт через подготовленную соседнюю папку, при ошибке rename исходный
путь восстанавливается; Git-история не сбрасывается. Повреждённый индекс,
отсутствующий снимок и несовпадение размера возвращают ошибку.

Переключение проверяет все игры, пропускает Ignore, блокируется при Missing,
запущенных играх или неизвестных процессах. Сначала сохраняется и коммитится
уходящий профиль, затем готовится целевой и меняются ссылки. При обычной ошибке
привязки или записи активного UUID уже изменённые ссылки откатываются. Общая
блокировка охватывает сценарий, запуск, изменение путей, настройки и RepoWorker;
она не удерживается при вызове UI. Аварийная остановка между заменами нескольких
папок не является атомарной транзакцией; полное автоматическое восстановление
после такого сбоя пока не реализовано. Игры, запускаемые извне SaveHub, не
подчиняются его mutex: не запускайте их во время файловых операций.

Команды конфликтов вызывают существующий RepoService. Обе файловые версии
сохраняются в Git metadata перед разрешением (включая KeepLocal/KeepRemote).
Эти технические резервные копии не выдаются за локальные снимки `SaveService`
и не отображаются как отдельные строки истории.
