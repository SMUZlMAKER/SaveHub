# Разработка

Важно: проект настроен на LF (`\n`), через `.gitattributes` включена конвертация к `LF`.

## Про фронтенд (Tauri + Svelte)

Фронтенд лежит во `frontend/`: Svelte 5 + TypeScript + Vite. Конфиг Tauri — `tauri.conf.json` в корне репозитория.

Нужны Rust (toolchain `msvc` на Windows), Node.js 24 и WebView2.

### Запуск для разработки

Из корня репозитория:

```bash
cd frontend
npm ci
npm run tauri dev     # vite dev-сервер + rust-приложение с hot reload фронта
```

Окно закрывается в трей; выйти — через пункт «Выход» в меню иконки в трее.

### Проверки

Из корня репозитория:

```bash
cd frontend
npm ci
npm run check
npm run build
cd ..
cargo test --locked
```

Перед Rust-тестами собираем фронтенд для встраиваемых ресурсов Tauri.

### Windows-установщик

Запускать из **Windows PowerShell/CMD**, с Windows-версиями Node.js и Rust MSVC
и установленными Visual Studio Build Tools с компонентами C++.
Обычная сборка в WSL создаёт Linux-приложение. Для Windows используйте эти команды
в Windows или ручной запуск GitHub Actions.

Из корня репозитория:

```powershell
cd frontend
npm ci
npm run tauri -- build --bundles nsis -- --locked
```

Tauri сам собирает фронтенд, Rust-приложение и NSIS-установщик.
Результат относительно **корня репозитория**: `target/release/bundle/nsis/*-setup.exe`.
Каталог называется `bundle`, без `s`, и появляется на этапе упаковки.
При явном `--target` путь — `target/<target-triple>/release/bundle/nsis/`;
при переопределении `CARGO_TARGET_DIR` вместо `target/` используется указанная директория.

`cargo build` собирает только Rust-код, `npm run build` — только фронтенд;
установщик эти команды не создают. С `--no-bundle` упаковка также пропускается.
После успешной упаковки Tauri выводит путь к `setup.exe` в конце лога.

NSIS устанавливает приложение для текущего пользователя. Если WebView2 отсутствует,
установщик скачивает его bootstrapper: для этого потребуется интернет. Сборки пока без подписи.

### CI и выпуск Windows-установщика

Workflow `.github/workflows/windows.yml` выполняется на Windows x64:

- В PR и после push в `main`: проверка Svelte/TypeScript, сборка фронтенда,
  `cargo test --locked` и release-сборка приложения без упаковки.
- Вручную: **Actions → Windows CI and release → Run workflow**, выбрать ветку.
  После проверок собирается NSIS `setup.exe` и публикуется GitHub Release.
  Для `main` это обычный релиз, для остальных веток — prerelease.
- Из открытого PR: оставить отдельный комментарий `/prerelease` без другого текста.
  Нужен write-доступ; поддерживаются ветки этого репозитория, но не форки.
  Собирается SHA головы PR на момент обработки команды, результат всегда prerelease.
  Ссылка на релиз появляется в Summary job публикации в Actions; бот в PR не пишет.

Для ручного запуска и команды из PR workflow сначала должен попасть в default-ветку.
Для проверок и пререлизов используется `GITHUB_TOKEN`. Для стабильных обновлений
нужен отдельный ключ подписи пакетов (см. ниже).
Право `contents: write` есть только у отдельной job публикации, которая не исполняет код PR.
Настройки организации/репозитория должны разрешать GitHub Actions создавать релизы.

Каждый выпуск получает уникальный тег `build-<run_id>-<run_attempt>` на собранном коммите.
Версии в `Cargo.toml` и `tauri.conf.json` должны совпадать; CI их не увеличивает.
В релизе указаны SHA коммита, ссылка на сборку и SHA256 установщика.
Установщик также доступен в Actions artifacts 14 дней. При ошибке загрузки останется
неопубликованный draft; повторный запуск создаст новый выпуск с новым тегом.

### Автообновление и автозапуск

SaveHub проверяет стабильные релизы GitHub при запуске и каждые 6 часов,
пока приложение работает, в том числе в трее. В настройках можно отключить
эти проверки или проверить обновления вручную. Установка — по кнопке,
с подтверждением и перезапуском приложения. Пререлизы автоматически не предлагаются.

Установщик включает автозапуск при входе в Windows. Его можно отключить
в настройках. При автозапуске приложение сразу уходит в трей.
Автоматическое обновление сохраняет этот выбор, удаление приложения убирает автозапуск.

### Ключи обновления — настроить один раз

Ключ нужен, чтобы приложение проверяло подлинность скачанного обновления.
Это отдельный ключ Tauri, не токен GitHub и не сертификат Windows.

1. В Windows PowerShell, из `frontend/`, создайте ключ вне репозитория:

   ```powershell
   npm run tauri -- signer generate -w "$env:USERPROFILE\.tauri\savehub.key"
   ```

2. В репозитории GitHub откройте **Settings → Secrets and variables → Actions**
   и добавьте:

   | Тип | Имя | Значение |
   | --- | --- | --- |
   | Variable | `SAVEHUB_UPDATER_PUBLIC_KEY` | Содержимое файла `savehub.key.pub` |
   | Secret | `TAURI_SIGNING_PRIVATE_KEY` | Содержимое файла `savehub.key` |
   | Secret | `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | Пароль, заданный при создании ключа |

Приватный ключ и пароль сохраните: они понадобятся для следующих обновлений.
Не добавляйте их в Git. Без публичного ключа приложение запускается,
но проверка обновлений недоступна.

### Бамп версии и выпуск обновления

Перед каждым стабильным релизом повышайте версию вручную. Например,
для исправления: `0.1.0` → `0.1.1`, для новой функциональности: `0.1.0` → `0.2.0`.

1. Укажите одинаковую новую версию в `Cargo.toml` (`[package].version`)
   и `tauri.conf.json` (`version`).
2. Из корня проекта выполните `cargo check`: он обновит версию пакета `savehub`
   в `Cargo.lock`. Включите все три файла в коммит с изменением версии.
3. После слияния в `main` откройте **Actions → Windows CI and release → Run workflow**
   и выберите `main`.

CI соберёт установщик, подпись `.sig` и файл `latest.json` для проверки обновлений.
После загрузки файлов релиз станет Latest. Версия должна быть выше предыдущей
стабильной: с такой же или более старой версией публикация завершится ошибкой.
Тег `build-…` создаётся автоматически и не заменяет бамп версии приложения.

Первую сборку с автообновлением нужно установить вручную. Следующие обновления
можно ставить из приложения. Перед первым выпуском проверьте установку и обновление
на Windows, в том числе с отключённым автозапуском.

Для локальной сборки с подписью задайте те же переменные окружения и из `frontend/` выполните:

```powershell
npm run tauri -- build --bundles nsis --config tauri.updater.conf.json -- --locked
```

Для разработчиков: параметры проверок лежат в `app_config_dir/updates.json`.
Адрес обновлений задан в `src/services/updates.rs` (`ENDPOINT`); при переносе
репозитория его нужно заменить. Релизы должны быть доступны без авторизации.

### Контракт фронт ↔ бэк

Запуск и обновления подключены к реальным настройкам и Tauri Updater.
Остальные ручки в `src/api/` пока — заглушки:
чтение отдает демо-данные, действия возвращают `ApiError::NotImplemented` (фронт покажет «Бэкенд пока не умеет: …»).
Где что подключать — помечено `TODO(backend)`. В `tauri dev` внизу каждого экрана видно, какие ручки он вызывает.

Правила:

- ручка — `#[tauri::command]` в `src/api/<экран>.rs`, регистрируется в `app::start` (`generate_handler!`);
- ручка тонкая: вызывает сервис или сценарий, переводит доменные структуры в DTO;
- DTO — структуры с `#[serde(rename_all = "camelCase")]` рядом с ручкой; их TS-двойники — во `frontend/src/lib/types.ts`, менять вместе;
- ошибки — `ApiError`: `NotImplemented`, `Rejected` (текст покажется пользователю как есть, например «Идёт игра, переключение недоступно»), `Internal`;
- долгие ручки (git, копирование сохранений) — `async fn`: синхронные ручки Tauri выполняет в главном потоке, окно зависнет;
- когда данные меняются не по запросу фронта (RepoWorker, запуск игры, трей) — шлем событие из `src/api/events.rs` (`app_handle.emit(...)`), фронт перезапросит данные.

| Экран | Ручки | Что подключить |
| --- | --- | --- |
| Игры | `list_games`, `add_game`, `set_game_save_path` | GameService, RuntimeState (запущенные игры) |
| Профили | `list_profiles`, `switch_profile`, `create_profile`, `delete_profile` | ProfileService, workflows::SwitchProfile |
| Снапшоты | `list_snapshots`, `restore_snapshot` | SaveService / снапшоты, сценарий отката |
| Настройки | `get_settings`, `update_settings`, `set_github_token` | хранилище Settings, системное хранилище токена |
| Запуск и обновления | `get_app_preferences`, `save_app_preferences`, `get_update_status`, `check_for_updates`, `install_update` | реализованы; настройки в `updates.json` |
| Шапка, трей | `get_sync_status`, `sync_now` | RepoWorker |
| Конфликты | `list_conflicts`, `resolve_conflict` | RepoWorker, сценарий разрешения конфликта |

Меню трея (`src/app/tray.rs`) пока живет на своей заглушке `TrayView::placeholder` — ее тоже заменить на данные из хранилищ.

## Архитектура, дизайн

Структура проекта

- `frontend/`: статика фронтенда
- `src/`:
  - `adapters/`: низкоуровневые адаптеры для взаимодействия с FS, git, процессами
  - `api/`: tauri-хэндлеры ("бэкенд"). Специальные функции, которые вызываются из tauri. Должны вызывать сервис или workflow в зависимости от сложности логики. Сами по себе - легковесные.
  - `app/`: корень и входная точка приложения. Читает и проверяет файл(ы), инициализирует структуры, сервисы, поднимает `tauri` и фоновый воркер.
  - `background/`: фоновый(-е) процесс(ы). В базовом виде - "следилка" за файлами. Реагирует на изменения, вызывает нужные сценарии (workflow) или сервисы.
  - `domain/`: доменные структуры (игры, профили)
  - `services/`: основная логика. GameService, ProfileService, SaveService, .... Каждый метод делает простое, гранулярное действие: "добавить новый профиль", "получить список всех игр".
  - `workflows/`: сценарии. Для сложных действий, по типу переключения профиля, требуется задействовать несколько сервисов - для того, чтобы не сорить ответственностью, такие сложные сценарии выносятся сюда.

### Взаимодействие

```text
Интерфейс ----> API ---+
                       |
                       +--> сервисы -> адаптеры
                       |
                       +--> сценарии -> сервисы -> адаптеры
                       |
Repo Worker -----------+
```

### Хранение данных внутри приложения

Чтобы не превращать хранение в кашу, предлагается организовать хранение данных следующим образом:

Хранилище есть структура, содержащая _внутри себя_ `RWMutex`.

Должны быть:
- Catalog (игры, профили, пути, настройки)
- RuntimeState (запущенные игры, подобные состояния "сейчас")
- Settings (базовые настройки: путь до репозитория, ссылка на удаленный репозиторий, локальные пользовательские данные)

Хранилища должны **создаваться** и **заполняться** в `app::start`, оборачиваться в `Arc` ([документация](https://doc.rust-lang.org/std/sync/struct.Arc.html)) и **передаваться** в конструкторы сервисов, где они нужны.

Хранилища должны **обновляться** по мере работы приложения: при разных пользовательских сценариях, рано или поздно вызывается какой-то сервис, этот сервис в свою очередь обращается к хранилищу и обновляет данные.

Справка Tauri: [Updater](https://v2.tauri.app/plugin/updater/),
[Autostart](https://v2.tauri.app/plugin/autostart/).
