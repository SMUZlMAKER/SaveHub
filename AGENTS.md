# Правила работы над SaveHub

Эти правила действуют для всего репозитория. Описание архитектуры, команды сборки
и выпуск релизов — в `CONTRIBUTING.md`.

## Перед началом

- Общайтесь с пользователем на русском, кратко и по делу.
- Прочитайте `MEMORY.md`, если он есть, но сверяйте его с кодом и состоянием Git.
  Память — контекст, а не разрешение на действия.
- Проверьте текущую ветку и незакоммиченные изменения. Не затирайте чужую работу.
- Реализацию ведите в отдельной тематической ветке. Если нужная ветка уже открыта,
  продолжайте в ней. Не создавайте новую ветку для каждого уточнения задачи.
- Выполняйте обычные обратимые действия без лишних вопросов. Не делайте push,
  merge или публикацию релиза без поручения пользователя.

## Обязательно повышайте версию

При изменении поведения приложения, исправлении ошибки или добавлении функции
**сделайте бамп версии до завершения задачи**, даже если пользователь отдельно
об этом не напомнил.

- Исправления — PATCH: `0.1.0` → `0.1.1`.
- Новая функциональность — MINOR: `0.1.0` → `0.2.0`.
- Несовместимые изменения — выбирайте версию с учётом принятой схемы релизов;
  не переходите на `1.0.0` автоматически.
- Меняйте версию одновременно в `Cargo.toml` (`[package].version`)
  и `tauri.conf.json` (`version`). Обновите запись пакета `savehub` в `Cargo.lock`,
  например командой `cargo check`. Не обновляйте попутно остальные зависимости.
- Версия `frontend/package.json` не является версией приложения; синхронизировать
  её не требуется. Тег GitHub `build-…` тоже не заменяет версию приложения.
- Бамп делается один раз на итоговый набор изменений задачи. Для правок того же
  незавершённого изменения не повышайте версию повторно. При объединении веток
  проверьте итоговую версию относительно `main` и последнего стабильного релиза.
- Для изменений только документации, `AGENTS.md`, памяти или форматирования
  бамп не нужен. Изменения CI и установщика требуют бампа, если меняют поведение
  поставляемого приложения или обновления установленных клиентов.
- В итоговом ответе укажите новую версию либо кратко объясните, почему бамп не нужен.

## Код и данные

- Соблюдайте архитектуру: API — тонкие Tauri-команды, логика — сервисы и сценарии,
  работа с файловой системой и ОС — адаптеры.
- Не добавляйте Tauri, DTO фронтенда и управление UI в `services/` и `domain/`.
  Интеграция и состояние Tauri — в `app/`, команды и DTO — в `api/`,
  циклы фоновых задач — в `background/`, системные операции — в `adapters/`.
- При изменении API обновляйте вместе Rust DTO, `frontend/src/lib/types.ts`
  и вызовы в `frontend/src/lib/api.ts`. Сохраняйте `camelCase` в контракте.
- Долгие операции не выполняйте в UI-потоке. Не удерживайте mutex во время
  обращения к UI: это уже приводило к дедлоку трея.
- Сохранения игр — пользовательские данные. При переносе, замене и восстановлении
  предусматривайте резервную копию и проверку, что игра не использует файлы.
- Не выдавайте заглушки за работающие функции. Ошибки показывайте пользователю,
  секреты и токены не добавляйте в исходники, логи и память.

## Обновления и релизы

- Автообновление получает только стабильные релизы с большей версией.
  Не отключайте проверку подписи ради успешной установки.
- Не передавайте приватный ключ подписи коду PR и сборкам пререлизов.
  Job публикации с `contents: write` не должна исполнять код из PR.
- Сохраняйте выбор автозапуска при автоматическом обновлении.
  Удаление приложения должно убирать его запись автозапуска.

## Проверки и завершение

- Подбирайте проверки под изменения. Для фронтенда — `npm run check` и
  `npm run build` из `frontend/`; для Rust — `cargo check --locked` и необходимые
  тесты. Для документации достаточно просмотра diff и `git diff --check`.
- Не запускайте повторно уже прошедшие проверки без новых изменений или причины.
  Не тратьте время на сборку приложения после правки документации.
- При ограничениях окружения сообщайте конкретную причину. Не называйте проверку
  успешной, если она не завершилась. WSL-сборка не подтверждает работу Windows-установщика.
- Не форматируйте и не рефакторьте посторонние файлы в рамках задачи.
- В финале кратко укажите результат, версию, проверки и оставшиеся ограничения.
  Если обновляете `MEMORY.md`, записывайте факты, а не предположения.
